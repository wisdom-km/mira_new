# 08 - 接缝、模块化与 Vibe Coding

> 原理库：为什么这样切、哪些能做、哪些不能做。批准者 Wisdom。
> 边界与契约仍以 `01` 为准；加删落点以 `07` 为准。本文件不复制技术栈、目录或 Command 清单。

## 一、核心命题

架构的核心不是「一开始就猜到以后所有功能」，而是先画清楚边界：

**哪一块可以独立加、独立删、独立坏，而不把整栋楼拆掉。**

大公司解决「很多人一起改、功能进进出出」的办法，几乎都是这件事。Vibe coding 把「很多人」换成「很多段没有共同记忆的对话」——接缝同样必要。

一句话：架构不是施工图，是**允许未来改主意的规则**。加功能是插上一块，删功能是拔掉一块。如果每加一刀都要切开整栋楼，不是功能太多，是一开始没有接缝。

## 二、为什么要沉淀，以及给谁用

聊天记录不作数（见 `00`/`06`）。0-1 用 vibe coding 走通 P0 之后，边界只活在仓库里才接得住下一轮对话。

本文件给：

- 人：解释为什么部分模块化，而不是「文件夹多看起来专业」
- AI：在动手前知道能改哪、不能发明哪
- 开源读者：克隆后不必还原一场讨论

## 三、先纠正一个误解

设计之初考虑增减功能，**不是把未来三年的需求都预埋进去。** 预埋会变成空接口、空表、空服务，没人敢删。

真正预埋的是接缝：

| 大公司预埋 | 本仓库对应（单仓桌面应用） |
|------------|------------------------------|
| 模块怎么说话 | Command、只读快照、`IRenderer` / `IModelLoader` 等接口 |
| 数据归谁管 | Script 管剧本结构，Scene 管节点，Link 管绑定，App 组装 |
| 发布和回滚 | 桌面 Demo 无灰度开关；靠主路径可运行 + git 回退 |
| 谁有权改哪一块 | CMake 链接图 + `07` 名词表（AI 也算「贡献者」） |

功能可以没有，**接缝必须先有。** 原则：为变化预留接缝，不为幻想预留房间。

因此 AI 模块保持空岛、不接线：接口缝在，房间空着不往里塞供应商。删按钮可以，堆空实现不行。

## 四、一张架构图要回答的六个问题

| # | 问题 | DirectorDesk 里怎么答 |
|---|------|------------------------|
| 1 | 系统拆成哪些块 | `01` 的模块与 `architecture.mmd` |
| 2 | 块与块只通过什么约定通信 | UI↔业务：Command / `AppViewState`；渲染：`RenderSceneView`；画布：`StoryboardSourceSnapshot` |
| 3 | 每块的数据谁说了算 | 剧本结构只来自 Script；机位属 Camera；绑定属 Link |
| 4 | 一块挂了，别的怎么办 | 解析失败有诊断；下载失败用缓存；导出失败不改场景图；AI 未接线故不能拖垮主路径 |
| 5 | 一块要换掉，要改几处 | 换 bgfx 实现应停在 `backends/`；换 OBJ 加载器应只加 `IModelLoader` |
| 6 | 一个功能上线/下线，要动几处 | 按 `07`：Panel → Command → visit → 快照。超过这条链还要改五个库，说明边界画错了 |

如果加一个按钮要改八个模块、三份持久化格式，先停下来改落点，不要继续堆。

## 五、大公司的分层，如何缩到本仓库

常见四层：体验、应用（用例）、领域、基础设施。规则：上面可以换，下面尽量稳。删一个入口不应倒逼改核心数据；加一个入口应只加适配，不复制业务。

| 层 | 本仓库 | 变化应停在 |
|----|--------|------------|
| 体验 | `UI::IPanel` | 快捷键、面板布局、文案 |
| 应用 / 用例 | App 消费 Command、组装快照 | 一次用户意图的编排 |
| 领域 | Script / Scene / Camera / Link / Storyboard / Asset / Export | 规则与所有权 |
| 基础设施 | Platform、`IRenderer`、`backends/`、curl | 窗口、GPU、HTTP、线程 |

专业说法：UI 可替换，领域逻辑只有一份。Storyboard 面板不得重新解析 Markdown，就是这条。

模块之间只依赖契约，不依赖对方肚子：调用 `开始加载(路径)` 或 `ApplyCameraPreset`，不翻 bgfx 句柄。对方内部用离屏 FBO 还是别的，调用方不管。这是面向接口，不是面向实现。

## 六、可增可删的几层设计——本仓库用哪些、不用哪些

### 1. 分层：让变化停在一层里

用。见上一节。删「在线资产页」不应倒逼改 Scene schema；加一个导出分辨率应停在 Export + 少量 UI。

### 2. 模块 + 接口

用。`IRenderer`、`IModelLoader`、`IHttpClient`、Command 变体都是契约。增减时：

- 加：新实现注册到已有接口，或新增一个 Command 值对象
- 删：去掉入口与 visit；不要让其它模块编译依赖已删实现的肚子

### 3. 可插拔（Plugin / Feature flag / Event / Capability）

**大部分先不用。** 单用户桌面 Demo 没有 1% 放量、没有多客户端探测。Command 队列已是「主干不知道面板怎么画」的钩子。不要为假想插件做空框架。

以后若有真实用户分流，再加配置开关；现在用 git 和 `07` 的删除分层代替「先关开关再删代码」。

### 4. 数据按谁拥有切开，不按页面切开

用。限界上下文在本仓库就是名词：剧本、场景、机位、绑定、画布、资产、导出。画布可以引用 `shotId`，但不该把剧本文本字段写进 Storyboard 的私有结构当唯一真相。

### 5. 康威定律 / 多团队

缩成：CMake 目标 + 文档地图。没有 200 人值班，但有持续接力的 AI。谁拥有模块，谁才能改它的肚子；跨模块只走公开头和快照。禁止为了方便去 include 对方 `.cpp` 内部。

## 七、好处与弊端

**好处**

- 主路径可以在功能进进出出时仍走完（剧本 → 资源 → 机位 → 画布 → 导出）
- 故障域清楚：闪屏在 Renderer，中文路径在 Platform，布局在 Storyboard
- 换实现有落点：新格式注册加载器，不改 Library 面板业务
- Vibe coding 的下一场对话有地图，不必从聊天里考古
- 删除有分层，避免 `AppViewState` 变成墓地

**弊端（必须接受，禁止用错误手段消肿）**

- App 会厚：它是合法编排者。痛了再在 App **内**分文件，不新开领域库（当前暂缓拆 `Application.cpp`）
- 快照会胖：这是 UI 隔离税。禁止把业务引用塞回面板来「消肿」
- 加一个按钮要跨 Panel / Command / visit，比在当前文件里写 if 慢
- 切错边界时，一个需求改五个模块——这时要重切名词，不是再拆第 14 个库
- 预留空岛（AI）有构建与心智成本；冻结它，而不是往里堆空房间

过度模块化（5 人拆 30 个服务、为三年后每个按钮建空表）比不模块化更糟。本仓库的对策是 **部分模块化**：控制面全留，模块数锁定，见 `07`。

## 八、Vibe coding 如何设计架构

Vibe coding 默认把逻辑写进「此刻打开的文件」，并把聊天当需求。对抗方式不是写更长的 Prompt 复制架构事实，而是：

1. **仓库内唯一事实源**：`docs/dev-map/`（`06` 只规定工作方式）
2. **硬门禁**：CMake 禁止 UI 链 GLFW/bgfx；公共头禁止泄漏第三方类型
3. **软门禁**：`07` 名词表；超出范围先停
4. **接缝先于功能**：Command / 快照 / 加载器注册表先有，具体预设和供应商后加
5. **结束时更新 `03`**，否则下一场对话会重新发明架构

能做：

- 在现有名词里加行为（新预设、新 Command、新 Panel、新 `IModelLoader`）
- 按 `07` 删除功能（入口 → Command → 快照 → 必要时整模块）
- 修某一故障域，不顺手改无关层
- 发现代码与地图冲突时停工，由负责人决定改代码还是改地图

不能做：

- 为单个按钮或假想功能新建 CMake 库、空服务、空表
- 在面板里解析剧本、算机位、调 bgfx、curl 供应商
- 把 Storyboard 接到 Script 对象上，或让后台线程改场景图
- 接线真实 AI、密钥 UI（AI 冻结，见 `07`）
- 用「以后可能用到」在主干焊死 if-else
- 跳过主路径去堆 Undo、时间轴、自由画布（范围改动先改 `00`/`03`）
- 把本文件或聊天当成第二份架构正文

## 九、加与删（思想）；步骤见 `07`

设计得好：新能力是独立名词或已有接口的新实现；UI 只多一个选择；失败时降级，不拖垮主路径。

设计得不好：在旧用例里塞 `if 官方 / if FBX / if 真 AI`；状态散落；一删某个入口，聊天或导出也编译不过。

差别不在聪明，在有没有稳定接缝。设计前应能回答：生命周期是什么、关掉要改几处、用户工程文件怎么办、最坏是否影响主路径。答不上来，不要合进主干。

删的勇气来自：入口可摘、数据有主人、主路径可在缺该块时仍运行、git 可回退。桌面 Demo 不做版本化 HTTP API 和灰度开关，不表示可以焊死。

## 十、设计之初预留什么

值得一开始就有：

- 模块边界和接口（`01`）
- 数据所有权（名词谁说了算）
- 日志与明确错误（Core）
- 异步交回值的队列（下载、大模型加载）
- 降级：清单失败用缓存、AI 未接线则主路径不依赖它
- 加删落点（`07`）

不值得一开始就有：

- 三年后每一个按钮
- 为假想功能建空表、空微服务、空供应商 SDK
- 功能开关平台、插件框架、多租户（用户规模到了再加接缝）
- 把 5 个人的桌面工具拆成 30 个进程

小团队最小做法（本仓库已经接近）：一个仓库；用例在 App；规则在领域模块；第三方在 `adapters`/`backends`；新功能先填进已有包，禁止直接改别人的核心结构，只引用稳定 ID；互相不 import 对方内部文件。删除 = 摘入口 → 观察是否还被工程文件需要 → 再删代码。这已是大公司同一思想的 80%，只是没有用更多服务把同一思想放大。
