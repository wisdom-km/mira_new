# 04 - 模型与人员交接规则（HOW TO SWITCH MODEL）

> 本文件保证不同 AI 模型或开发者接手时，不依赖聊天记忆也能安全继续。

## 一、接手前必读顺序

任何接手者在修改文件前必须完整阅读：

1. `00-VISION-AND-CONSTRAINTS.md`
2. `01-ARCHITECTURE-MAP.md`
3. `02-ROADMAP.md`
4. `03-CURRENT-STATUS.md`
5. `05-CODING-STANDARDS.md`
6. 当前 Phase 涉及的 `modules/*.md`

然后检查仓库状态、当前分支、最近提交和已有 tag。若仓库实际状态与 `03` 不一致，**停止实现**，先记录差异并向用户确认；不得自行猜测哪个状态正确。

## 二、接手者必须回答的五个问题

开始工作前，在内部或工作记录中确认：

1. 当前处于哪个 Phase？
2. 当前 Phase 已完成、未完成的 Task 分别是什么？
3. 本次请求是否属于当前 Phase？
4. 将修改哪些模块，它们的依赖方向是否合法？
5. 本次完成后用什么测试和验收标准证明成功？

任一问题无法回答时，先补充调查或请求澄清，不得直接编码。

## 三、工作规则

- 一次只推进当前 Phase；禁止“顺手”实现后续功能
- UI 不写业务逻辑，只产生 Command、读取只读 State
- 新能力必须放入正确模块；不为方便而增加反向依赖
- 公共接口修改前先检查全部调用者和数据契约
- 不修改锁定技术栈；确需修改时走“架构变更流程”
- 不用临时 hack 绕过验收；阻塞必须写入 `03`
- 不覆盖、回滚或删除无法确认来源的现有更改
- 不自行 commit、tag、push；必须有用户明确授权

## 四、架构变更流程

当现有架构无法满足当前 Phase 时：

1. 给出可复现的技术证据，而不是偏好；
2. 说明至少一个不改变架构的替代方案；
3. 说明建议变更对模块、数据格式、路线图和兼容性的影响；
4. 获得用户明确批准；
5. 先更新受影响的 dev-map 文档，再实施代码变更；
6. 在 `03-CURRENT-STATUS.md` 的“已确认决策”和工作日志中记录。

未经批准不得改变技术栈、Phase 顺序、核心用户路径或 P0 边界。

## 五、工作结束时的强制交接

每次工作结束必须更新 `03-CURRENT-STATUS.md`，最少包含：

- 当前 Phase 和状态；
- 本次实际完成内容；
- 实际验证命令与结果；
- 未完成项、失败测试和阻塞；
- 新增决策与已知风险；
- 下一步唯一允许执行的任务；
- 涉及的关键文件。

如修改了数据格式或公共接口，还必须同步更新对应 `modules/*.md` 或 `01-ARCHITECTURE-MAP.md`。

## 六、Phase 完成检查

Phase 只有满足以下条件才算完成：

- `02-ROADMAP.md` 中本 Phase 所有 Task 和验收项均有证据；
- Windows 与 macOS CI 满足该 Phase 要求；
- `03` 已更新为“等待提交/tag”或“已完成”；
- 用户确认可以提交；
- 提交成功后由用户明确要求才创建约定 tag；
- tag 创建后，`03` 才能把“下一个允许工作”切到下一 Phase。

**禁止仅因为代码看起来完成就进入下一 Phase。**

## 七、推荐交接摘要模板

```markdown
## 交接摘要
- 当前 Phase：
- 本次完成：
- 修改文件：
- 验证结果：
- 未完成/阻塞：
- 新增决策：
- 下一步唯一任务：
- 是否已提交/tag：
```

该摘要用于沟通；`03-CURRENT-STATUS.md` 仍是唯一真实来源。
